> 输入任意语料的**统计特征** → **O(1) 大字典查表**直接得到最优 BM25 超参数（k1 / b / k3 / δ / IDF）；查不到就启发式兜底。16 个 BEIR 数据集验证：**16/16 不劣于默认参数、NDCG@10 中位数 +18.0%（均值 +30.5%）、留一语料集词典命中率 92.0%**。

> 😄 或许我们应该叫 **BM26**？——参数都能自适应了，版本号也自适一下（开个玩笑，BM25 还是 BM25）。

## 为什么需要它

BM25 是信息检索最常用的排序模型，但它的**最优超参数随语料变化极大**——短文本、长文本、代码、法律文书、问答社区，各自的最优 k1/b 完全不同。实际工程却永远用 `k1=1.2, b=0.75` 的默认值，因为调参需要带标注的验证集，而新语料往往**没有标注**。

AutoBM25 换了一条路：**最优参数是语料统计结构的函数**，而统计结构不需要标注就能测量。测量出 18 维统计特征，查表即得参数——零标注、零调参、常数时间。

## 亮点

- 🗂️ **18 维统计特征**（P0/P1/P2）：文档长度分布、词频冗余度、词汇增长曲线、查询侧特征——每个特征都有明确的"机制假设"（为什么它能预测某个参数）
- ⚡ **O(1) 参数大字典**：`特征向量 → 最优参数` 最近邻查表，含**分布外（OOD）防护**与**启发式回退**；48 个条目随包提交（16 个基准语料 + 32 个跨域拼接语料），每条都在来源语料的全部查询上验证过不劣于默认参数
- 🔧 **k3 查询词频饱和项**：消融试验确认有效，长查询场景相对提升最高 **+19.9%**
- 🧩 **多语料拼接（Mixing）**：把已有语料组合拼接生成"跨域样本"，主动在特征空间补点，词典命中率 **70.6% → 92.0%**
- 🚀 **规模验证到 884 万文档**（msmarco），全自研 numpy 向量化 BM25/BM25+ 引擎，超大数据集流式子采样、相关标注全保留
- 🦀 **Rust/PyO3 加速**：分词建索引阶段提供编译扩展，**端到端快 4.6–9.3×**，打分逐位一致（可选，纯 Python 依旧可用）

这些数字是怎么来的（读表前值得知道）：

- 每个字典条目都是在该语料的**全部查询**上从候选池里选出来的，而候选池里始终包含 BM25 默认参数
  —— 因此一个条目不可能是它来源语料上"比默认更差"的参数；表格量的就是上线路径本身（查字典，
  未命中则回退启发式）。
- dbpedia-entity、climate-fever、fever、hotpotqa、msmarco 五个语料被降采样到 20–30 万篇文档。
  采样时会**保留全部标注相关文档**，所以绝对数值不能与全量 BEIR 榜单直接比较；每一格的两个数字
  都取自同一份采样、同一批查询与标注。
- 如果语料不在字典里，参数来自最近的条目或启发式。把目标语料自己的条目排除后，字典仍覆盖
  **92.0%** 的目标（16 个语料 + 34 个跨域混合语料，共 50 个）。

## 快速开始

```bash
pip install .
```

然后直接把语料交给它 —— 传一个字符串列表就够了，不需要学任何文件格式：

```python
from autobm25 import AutoBM25

corpus = [
    "BM25 is a probabilistic ranking function used in information retrieval.",
    "Automatic parameter tuning improves retrieval effectiveness.",
]
retriever = AutoBM25()
retriever.index(corpus)                  # 直接传字符串列表即可，不依赖任何文件
print(retriever.params)                  # 该语料自动选出的超参数
retriever.search("parameter tuning", top_k=5)
```

`corpus` 可以是任何"列表状"的东西：字符串、`{"id", "text"}` 记录、dataframe 的某一列、从接口
拉回来的文档。整个过程不写盘，也不要求任何目录结构。`index(corpus, queries=[...])` 再把查询
一起传进去，查询侧统计量（查询长度、查询词在语料中的覆盖、idf）会并入同一个特征向量。

语料已经在磁盘上了？把目录交给 CLI 即可 —— 它只是同一套 API 的便利封装，不是硬性要求：

```bash
autobm25 --dataset dataset/XXX                 # 批量：跑 queries.jsonl → results.jsonl，有 qrels 就顺带评测
autobm25 --dataset dataset/XXX --interactive   # 交互式：输入查询 → 回车出结果，exit 退出
autobm25 --demo                                # 内置语料，一个文件都不用准备
```

启动时会打印一条日志，显示本数据集自适应选择的 BM25 超参数（如 `k1=0.5 b=0.495 k3=0.7 δ=0.97 idf=smoothed`）。

参数字典随包内置（`autobm25/data/param_dictionary.json`），`pip install .` 后开箱即用，无需先跑任何实验。

想先看效果？`autobm25 --demo` 会索引一份内置的小语料（十篇自己编的文档，分别讲冲煮、骑行和检索），打印自动选出的超参数和几条查询的排序结果，不需要任何数据集目录；`autobm25 --demo --interactive` 可以直接对这份语料输入你自己的查询，`python examples/quickstart.py` 则是同一件事的可复制脚本（语料是一份编出来的客服 FAQ）。

## Rust 加速（PyO3）

检索内核同时提供了一份 Rust 实现，通过 **PyO3** 编译成 Python 扩展模块：热点循环跑在编译代码里，而对外接口、特征定义和排序结果与上文完全一致。

该扩展是**可选**的。单独 `pip install .` 仍然使用纯 Python 实现；编译模块不存在时，所有入口都会自动回退到纯 Python——`autobm25.BACKEND` 会告诉你当前用的是哪一个，设置 `AUTOBM25_NO_RUST=1` 可以强制走 Python。

### 哪些阶段走了 Rust

整条 pipeline 是：加载 → 分词建索引 → 特征 → 预测 → 检索。扩展覆盖中间的三个阶段以及打分；
剩下两个用 Python 是刻意的选择。

| 阶段 | 实现 | 成本 |
|---|---|---|
| 加载文档与查询 | Python | I/O + `json` 解析；几 GB 的语料文件要几秒到几十秒——这正是加载器**没有**进 Rust 的原因 |
| 分词 + 倒排索引（`build_index`） | **Rust** | 一遍扫过语料，同时把特征统计也收齐 |
| 特征向量（`extract_features`） | **Rust** | 直接读取这一遍的统计量，不再重复分词 |
| 参数预测（查字典 + 启发式） | Python | O(1)：48 条 × 21 维，**每个语料 0.1–0.5 ms**，config/字典都带缓存 |
| `search` / `search_many` | **Rust** | posting list 累加、释放 GIL、每个工作线程独立 scorer |
| 评测指标（CLI 批量模式） | Python | 对返回的排序做 numpy 平均，毫秒级 |

加载器留在 Python，是因为它本质是 I/O + JSON 解析——在几 GB 的语料上它就是墙钟时间的大头，
换成 Rust 也不会让磁盘读得更快。参数预测留在 Python 则是另一个原因：它本身就是常数时间查表，
向量化没有收益。想在自己机器上复现分段耗时：
`python research/stage_profile.py --dataset scifact [--no-rust]`。

瓶颈**不在打分**——那部分本来就已经是 numpy 向量化。瓶颈是**一个遍历全语料每个 token 的 Python 循环，每个 token 做一次字典操作，而且整段跑了两遍**：一遍算统计特征，一遍建倒排索引。

### Rust 扩展替换掉了什么

| 阶段           | Python                                                           | Rust                                                             |
| -------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------- |
| 分词与词频统计 | `str.lower().split()`，每个 token 一次字典操作                 | 单遍扫描语料；词项放在扁平表里，只有词项首次出现时才哈希字符串   |
| 统计特征       | 重新分词每个文档，并且在内存里为**所有**文档各保存一份字典 | 直接复用建索引那一遍的副产品——语料只分词**一次**         |
| 倒排索引       | 对 Python 侧攒出来的 posting 列表逐词项`np.asarray`            | postings 在同一遍里直接建好                                      |
| BM25 打分      | 已向量化，但用`np.add.at` 散射累加，且每个查询都要对全数组排序 | 沿 posting 列表累加、每个查询零分配、释放 GIL、每线程一个 scorer |

因此 `index()` 对整个语料只分词一次而不是两次，这是收益最大的一处改动。纯 Python 版的 `BM25Engine` 原样保留，仍然可用。

### 用户需要装 Rust 吗？不需要

PyO3 是**编译期**工具：Rust 代码只在打包时编译一次，编译产物就是一个普通的 Python 扩展模块，最终分发出去的是它。使用者只需照常导入，不需要编译器、不需要工具链、不需要任何额外步骤：

```python
import autobm25                       # 有编译好的扩展就自动加载

retriever = autobm25.AutoBM25()       # 底层就是 Rust
retriever.index(corpus)               # 整语料只分词一遍
retriever.search("parameter tuning", top_k=5)

print(autobm25.BACKEND)               # "rust"
```

把这套包交给别人，有三种方式：

| 分发方式                                                                | 对方需要什么                                                                              |
| ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 直接给编译好的 wheel，如`dist/autobm25-0.1.0-cp39-abi3-win_amd64.whl` | 只需`pip install <wheel>`，扩展就在包里                                                 |
| 把各平台 wheel 发到包索引                                               | 只需`pip install autobm25`，pip 会自动选匹配其系统/CPU 的那个                           |
| 直接给源码仓库                                                          | 装了 Rust 的人`pip install .` 会自动编译出加速版；没装的人也照样能用，只是退回纯 Python |

`abi3-py39` 的含义是：**同一平台上**一份 wheel 就能服务 CPython 3.9 及之后所有版本，所以构建矩阵按操作系统/架构（`win_amd64`、`manylinux_x86_64`、`macosx_arm64` …）来分，而不是按 Python 版本分。做不到"一个 wheel 通吃所有平台"——编译扩展天然与平台绑定；这也是为什么源码仓库里没有编译产物时，打出来的是 `py3-none-any` 纯 Python wheel。

而且这一步永远不会出事：`autobm25/_accel.py` 有扩展就用、没有就回退纯 Python，所以 `import autobm25` 绝不会因为缺二进制或二进制不匹配而失败，只是慢约 7 倍。`AUTOBM25_NO_RUST=1` 可强制走 Python，`autobm25.backend_info()` 会告诉你当前用的是哪一个。

你可以自己验一遍：

```bash
python _bench/verify_wheel.py
```

它会打一个 wheel、装进临时目录，然后在一个 `PATH` 里没有 `cargo`、`CARGO_HOME` / `RUSTUP_HOME` 指向不存在目录的子进程里导入它，并断言底层确实是 PyO3 扩展、`AUTOBM25_NO_RUST=1` 也确实能正常工作。

### 自己编译

```bash
python rust/build_pyext.py             # 等价于 cargo build --release --features python
python rust/build_pyext.py --check     # 编译并验证能否导入
```

产物会安装到包内 `autobm25/_autobm25_rs.pyd`。使用 `abi3-py39` 构建，一份二进制可服务 CPython 3.9 及以上。工具链会依次尝试：先默认的，再尝试已安装的 `*-windows-gnu`——因为默认的 MSVC 工具链若没装 Visual C++ 链接器会在链接阶段失败，而旁边的 MinGW 可以正常用；也可以 `--toolchain <name>` 直接指定。`rust/` 下的 `autobm25-rs` 命令行程序只需 `cargo build --release`，完全不依赖 Python。

一般不需要手动跑：`setup.py` 会在 `pip install .` / `pip wheel .` 时，若发现没有编译产物且 `cargo` 在 PATH 上，就自动编译一次；已有产物则直接复用。设置 `AUTOBM25_SKIP_RUST_BUILD=1` 可跳过。

### 实测加速

12 个逻辑核，CPython 3.11.5，numpy 1.26.4。同一台机器、同一份数据、同一个进程，`top_k=100`；Python 一列是同一个包加上 `AUTOBM25_NO_RUST=1`。

| 数据集        |  文档数 | token 数 | 查询数 |                          建索引+特征 |                     检索（全部查询） |                               端到端 |
| ------------- | ------: | -------: | -----: | -----------------------------------: | -----------------------------------: | -----------------------------------: |
| arguana       |   8,674 |   145 万 |  1,406 |  1.79 s → 0.25 s（**7.3×**） | 3.43 s → 0.24 s（**14.3×**） |  5.28 s → 0.57 s（**9.3×**） |
| scifact       |   5,183 |   111 万 |  1,109 |  1.33 s → 0.15 s（**9.1×**） |  0.33 s → 0.07 s（**4.8×**） |  1.71 s → 0.26 s（**6.5×**） |
| nfcorpus      |   3,633 |    85 万 |  3,237 |  0.99 s → 0.12 s（**8.3×**） |  0.31 s → 0.07 s（**4.1×**） |  1.42 s → 0.31 s（**4.6×**） |
| trec-covid-v2 | 129,179 |  2717 万 |     50 | 36.04 s → 3.78 s（**9.5×**） |  0.34 s → 0.06 s（**5.7×**） | 37.39 s → 4.86 s（**7.7×**） |

*端到端* = 加载 + 参数预测 + 建索引 + 特征 + 检索。若按拆分调用（`extract_features` 与 `build_index` 各自分词一遍）计，则是 **3.4–7.0×**。

怎么读这张表：Rust 侧分词建索引约 **720 万 token/s**，Python 侧约 **75 万 token/s**；而且语料越大差距越大，因为 Python 的开销与 token 数成正比、且每个 token 都要碰一次字典。检索的提升在长查询场景最明显（arguana，14.3×），因为旧的 `np.add.at` 散射累加在那里最慢；批量路径会释放 GIL 并吃满所有核。

### 一致性

`python _bench/bench_backend.py <dataset> --compare` 会在同一份数据上跑两套后端，逐项比对特征向量、选出的超参数、每个查询的完整排序，以及 MRR@10 / NDCG@10 / Recall@100。在 scifact、nfcorpus、arguana、trec-covid-v2 上：

- 特征值差异 ≤1e-11（同一批数字、不同的浮点求和顺序所致），选出的超参数完全相同；
- 所有排序逐位一致，**唯一例外**是文档在 `top_k` 截断处**并列同分**时：`np.argpartition` 会从并列分组里任取一个，而 Rust 采用 Python 代码自己写明的 tie-break（文档下标小者优先）。两者分数逐位相同，MRR@10 与 NDCG@10 不受影响；当第 100 名那个并列文档恰好在其中一边被判为相关时，Recall@100 会有第 4 位小数级别的差异。

## 把数据交给它

AutoBM25 只要两样东西——文档和查询——怎么存是你的事。**没有强制目录、也没有强制格式**：

| 你手上是什么 | 怎么交给它 |
|---|---|
| 内存里的列表 | `retriever.index(docs)`，字符串或 `{"id", "text"}` 都行 |
| dataframe / 数据库 / 接口 | 拼成同一个列表（`[{"id", "text"}]` 或纯字符串）后调用 `index()` |
| 磁盘上的文件 | `AutoBM25.from_dataset("path/")`，或 CLI 的 `autobm25 --dataset path/` |

`from_dataset` 只是便利封装，不是契约：它会自动识别常见的两种目录布局——简单格式
（`docs.jsonl`、`queries.jsonl`、`qrels.jsonl`）和 BEIR 格式（`corpus.jsonl`、
`queries.jsonl`、`qrels/*.tsv`）——除此之外做的和手动 `index(docs)` 完全一样。
**文档是唯一必需的输入**，查询可以交互式输入，qrels 只有想让 CLI 顺带打印评测时才需要。

## 局限

- **分布外（OOD）**：每个条目是在它自己的来源语料上验证的，不是你手上的语料。把目标语料自己的
  条目排除后，字典在上表 16 个语料上仍有 75% 命中率——但此时它是在"拿别的语料"做预测，这不是
  免费的：留一语料（leave-one-out）设置下 12/16 有提升（均值 +17.0%，中位数 +7.7%），
  4 个低于默认参数（-8% 到 -23%：fiqa、arguana、climate-fever、vihealthqa，其中三个是字典
  未命中、直接落到启发式）。OOD 防护和启发式兜底能限制损失，但消除不了它。如果你的语料在字典里
  没有对应物，请先验证它给出的参数再上线。
- **非英文语料**：特征含英文停用词密度等语言相关项，非英文语料（如越南语 vihealthqa）需要语言无关特征或独立分册。
